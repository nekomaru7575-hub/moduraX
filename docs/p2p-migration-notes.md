# P2P化の下調べ

Renderへデプロイできない間の検討メモ。**このディレクトリ（trpg-app-w2p）は実験用のコピー**で、
本体（trpg-app）とは別物。ブランチは `w2p-migration`。

## 1. いま「サーバー」が持っている仕事は4つある

P2P化の話をする前に、`server/index.js`（3051行）が何をしているかを分けておく。
全部が同じ理由でサーバーにあるわけではないので、まとめて論じると判断を誤る。

| # | 仕事 | 該当 | P2P化との関係 |
|---|---|---|---|
| A | 静的配信 | `serveStaticFile` 他 ~120行 | **P2Pと無関係**。Pages系へ置けば済む |
| B | 状態の一元化（WebSocket） | `wss.on('connection')` ~465行 | **ここがP2P化の本体** |
| C | 永続化 | Upstash Redis（`readRoomState`/`writeRoomState`/`schedulePersistForRoom`） | P2Pだと**置き場所が無くなる** |
| D | 秘密鍵を持つ中継 | R2アップロード・キャラシ取り込み・BCDiceキャッシュ ~1200行 | **P2P化できない**（後述） |

つまり「P2Pに載せ替える」で消せるのはBだけで、A・C・Dはそれぞれ別に始末が要る。

## 2. Bをどう移すか — 案は2つ、実質1つ

いまの同期は**サーバー権威**。クライアントは自分の画面へ先に反映してから `ACTION{action,payload}`
を投げ、サーバーが同じreducer（`js/game-store.js`をサーバーもimportしている）へ適用し、
Redisへ保存し、他の全員へ配る。順番を決めているのはサーバー1点。権限判定
（`GM_ONLY_ACTIONS`・`verifyIdentity`・入室パスワード）もそこにある。

### 案1: ホスト権威型P2P（推奨）

GM（部屋を建てた人）のタブが、いまのサーバーの役をそのまま引き受ける。他の参加者は
GMとだけ WebRTC DataChannel で繋がる**スター型**。

- `js/net-sync.js` は「送る／受け取る」の口だけなので、**トランスポートの差し替えで済む**。
  プロトコル（INIT / ACTION / RESYNC / TYPING_USERS / ENTRY_REQUIRED …）は変えなくてよい。
- `wss.on('connection')` の中身（~465行）を、ブラウザで動く「ホスト役モジュール」へ引っ越す。
  Node依存（`ws`・`node:crypto`）を `RTCDataChannel`・`crypto.subtle` へ置き換える程度。
- **差分が読める規模で収まるのはこの案だけ。**

### 案2: CRDT（Yjs / Automerge）

権威を無くして真のメッシュにする案。`js/game-store.js` は3716行・43 export の
命令的なreducerで、CRDTのデータモデルとは前提が違う。**全面書き換えになるので現実的でない。**
プラグイン（シノビガミ・DX3・ステラナイツ等）が全部この上に乗っているので巻き添えも大きい。

→ **案1で進める前提で以下を書く。**

## 3. 正直に詰まるところ

### 3-1. シグナリングサーバーは結局要る
WebRTCは相手を見つけるのに必ず仲介が要る。「サーバーが無くなる」わけではなく、
**常時起きている大きなサーバーが、繋ぐ瞬間だけの小さなサーバーになる**という話。
公開シグナリング（Trysteroのnostr/MQTT、PeerJSの公開サーバー）に乗る手はあるが、
他人のインフラに部屋の生死を預けることになる。

### 3-2. NAT越え（TURN）
Symmetric NAT下ではSTUNだけでは繋がらず、TURN中継が要る。実測で1〜2割は踏む。
無料TURNは選択肢が乏しく、**「たまに繋がらない人が出るセッションツール」**は
TRPGの用途だとかなり痛い。ここが一番のリスクだと思う。

### 3-3. GMが落ちたら部屋が消える
いまはRedisに `room:room-N` があるので、全員が抜けても部屋は残る。ホスト権威P2Pだと
状態はGMのタブの中にしか無い。**GMがタブを閉じた／回線が切れた＝セッションが飛ぶ。**
- 緩和: IndexedDBへ保存してリロードで復帰、定期の自動エクスポート。
- ただし「GMが落ちてる間、他の人は何もできない」のは緩和できない。

### 3-4. R2アップロードはP2P化できない
`/api/image` `/api/audio` はR2の署名にアクセスキーが要る（`server/r2.js`）。
ブラウザへ鍵を置けば**そのまま流出＝課金事故**で、これはメモリに残した脅威モデルの
「守る対象」ど真ん中。選択肢:
- (a) 署名発行だけの極小関数を残す（＝完全なサーバーレス化は諦める）
- (b) 画像をDataChannelで直接配る（音源20MBはつらい。`js/image-upload.js` は6モジュールから使われている）
- (c) アップロード機能を落として外部URLのみにする

### 3-5. キャラシ取り込みはCORSで直叩きできない
`/api/character-sheet` は「外部のキャラクターシート置き場がCORSを許していないので代わりに取りに行く」
中継（`server/index.js` のコメントに明記）。**ブラウザからは代替不能**。3-4と同じく、
極小の中継を1つ残すか、機能を落とすか。

### 3-6. BCDiceは直叩きできる（ここは朗報）
`js/BCdice.js:4` が既に `https://bcdice.onlinesession.app` をブラウザから直接叩けている
＝CORSは通る。`/api/bcdice/*`（カタログ・システム情報）はキャッシュと堅牢化のための
proxyであって、**CORS回避ではない**。直叩きへ寄せられる。

### 3-7. 部屋一覧が無くなる
`/api/rooms` の一覧・作成・パスワード設定（`js/room-index.js`）はサーバー前提。
P2Pだと「GMが出したURL（部屋ID＋シグナリング情報）を配る」形になる。

## 4. 段階の提案

**Step 0 と Step 1 は P2P化の成否と無関係に効く**ので、そこから触るのが安全。

| Step | 内容 | 効果 | 戻せるか |
|---|---|---|---|
| 0 | 静的配信をPages系へ分離（A） | デプロイ問題の半分がここで解決する | 容易 |
| 1 | BCDiceカタログを直叩きへ（3-6） | サーバー依存が1本減る | 容易 |
| 2 | `js/net-sync.js` のトランスポートを差し替え可能に抽象化 | WS版とRTC版を並走できる | 容易 |
| 3 | ホスト役モジュール（`wss.on('connection')` の移植） | ここが本番 | **重い** |
| 4 | IndexedDB永続化＋自動エクスポート（3-3の緩和） | GM落ち対策 | 中 |
| — | R2・キャラシ中継（3-4/3-5） | **極小サーバーとして残す判断が要る** | — |

## 4-b. 実験の結果（2026-08-21）

Step 1・2・Bまで実装して確かめた。**ホスト権威型P2Pは成立する。**

実装したもの:

| ファイル | 役目 |
|---|---|
| `js/net-transport.js` | 契約と実装の選択、切断コードの意味 |
| `js/net-transport-ws.js` | 今までどおりのWebSocket（挙動は据え置き） |
| `js/net-transport-rtc.js` | ゲスト側。ホストとDataChannelを張る |
| `js/net-signaling.js` | SDPとICE候補を運ぶ細い口（サーバー経由） |
| `js/net-host.js` | ホスト役。`wss.on('connection')` の最小移植 |
| `js/room-authority-rules.js` | GM限定の判定を画面・サーバー・ホストで共有 |
| `server/index.js` | `SIGNAL_HELLO` / `SIGNAL` の中継（中身は解釈しない） |

`npm run dev` で3タブ（ホスト1＋ゲスト2）を確認:

- DataChannelが張れ、`INIT` がP2Pで届く
- チャット・コマがホスト⇔ゲスト双方向に流れ、ゲスト→ホスト→別ゲストの中継も通る
- ゲストのGM限定操作をホストが断り、`RESYNC` で戻る
- 名乗った直後の連続操作が弾かれない（非同期検証のキューが効いている）
- **サーバーの `server/rooms/room-3.json` は空のまま**——コマも発言も参加者も、
  1件もサーバーを通っていない。同期データが本当にP2Pへ移ったことの一番強い証拠
- ホストが居ない部屋で `?net=rtc` を開くと8秒で諦め、WebSocketへ落ちる（併存の実体）

### 前節の見立てとずれた点

**3-1（シグナリングは結局要る）はその通りだったが、思っていたより軽い。** 中継は
`SIGNAL_HELLO` と `SIGNAL` の2つだけ、中身は解釈しない郵便受けで済んだ。

一方、**下調べで見えていなかった落とし穴が3つあった**（いずれも実装で踏んだ）:

1. **GMのタブに2つ目の `ImmutableStore` を作れない。** `store` も `EventBus` も
   モジュール・シングルトンで、コミットのたびに `STATE_CHANGED` が飛ぶ。サーバーの
   `entry.store` に当たるものを新設すると画面が壊れる。→ GM自身のストアを権威にする。
2. **本人確認が sync → async になる。** サーバーの `verifyIdentity` は `node:crypto` で
   同期だが、ブラウザは `crypto.subtle` で非同期。await の間に届いた操作を先に処理すると、
   名乗り済みの人がゲスト扱いで断られる。ピアごとのキューが要る。
3. **GM限定の判定の写しが増える。** `GM_ONLY_ACTIONS` はサーバーにしか無く、
   `canOperateAsGm` は2か所にあった。ホストが3つ目を持つと事故が確定するので、
   純粋モジュールへ寄せた。

### まだ移していないもの

記入中（TYPING_*）・スタンプ・送信音・部屋の削除・入室パスワード・メッセージ流量制限、
そして**永続化**。永続化が無い＝ホストのタブを閉じた時点で部屋が消える（3-3のまま）。
残るのは移植量の問題で、成立するかどうかの問題ではなくなった。

## 5. 結論（現時点）

**「サーバーを完全に無くす」は達成できない。** R2アップロードとキャラシ取り込みが
秘密鍵とCORSで縛られているため、どう転んでも小さな中継は残る。

得られるのは「常時起きているNodeプロセスが要らなくなる」ことで、失うのは
**繋がりやすさ（TURN）と部屋の永続性（GM落ち）**。TRPGのセッション中に落ちると
被害が大きい種類の機能なので、**3-2 と 3-3 を許容できるかが判断の分かれ目**。

まずは Step 0（静的配信の分離）だけ試して、デプロイの詰まりがそれで解けるかを
見るのが費用対効果が良いと思う。
