# .loop — ループエンジニアリング最小構築

1タスクを「発注 → 実装 → 機械ゲート → 検査 → 修正」の閉ループで回すための仕組み。

## 状態: 実装役を「親方」化（2026-08-07）

実装役の Sonnet は**親方**として動く。コードを1回だけ読み、機械的な書き換えを
無料のローカルLLMに切り出して発注し、残りを自分で実装する。ローカルLLMの起動も親方が行う。

Gemini は引き続き使えない（後述）。

### なぜ親方に変えたか

それ以前は統括役（Opus）が発注書の `## LOCAL TASKS` を書く設計だったが、これは矛盾していた。
統括役には「ソースファイルを読むな」という鉄則があり、関数名も中身も知らずに
`ファイルパス :: 関数名` と英語の書き換え指示は書けない。結果、LOCAL TASKS はほぼ空になった。

| | 実績 |
|---|---|
| 回したタスク | T-001 / T-002 / T-003 |
| `## LOCAL TASKS` があった発注書 | T-002 のみ |
| ローカルLLMが実装したユニット | 1件（3タスク合計） |

`function` 宣言はこのリポジトリに 470 件あり（アロー 56 / メソッド様 293）、**対象が
少ないから使われなかったのではない**。ソースを読める者が仕分けをしていなかったのが原因。

分割役を別工程で立てる案は採らなかった。分割役と実装役で**同じコードを2回読む**ことになり、
読み込みが支配的なこのループでは（T-001 の実装役 102k はほぼ探索）分割の利得を食い潰す。

### この変更で浮く分

読み込みトークンは浮かない（親方は結局読む）。浮くのは編集の出力分と、その後の周回。
ゲート FAIL や検査指摘が関数内で閉じる修正なら、Sonnet を立て直さずローカルへ回せる。
再開が安くない（T-001 で 102k → 115k）ことを踏まえると、周回側の効果のほうが大きい。

### 計測: なぜローカルLLMを入れたか

T-001（Sonnetのみ）の実測は次のとおり。

| 工程 | モデル | トークン |
|---|---|---|
| 実装 1回目（NEED-ALLOW で停止） | Sonnet | 101,971 |
| 実装 2回目（再開して完遂） | Sonnet | 114,667 |
| 検査 | Sonnet | 78,935 |
| 機械ゲート ×2 | — | 0 |
| 合計 | | 295,573 |

通常プロンプトで同じ実装をした場合の見積もりは 100〜150k（すべて Opus）。トークン数では
明確に増、Sonnet の単価を考慮した金額ではほぼ互角。本来はこの 217k の実装分が Gemini 側に
出て Claude の消費がゼロになる設計だった。

得られたものは、独立した検査が仕様との食い違いを1件検出したこと、機械ゲートが無料で
効いたことの2点。

### ローカルLLM実装役の使い方

```powershell
powershell -File .loop/probe-local.ps1                    # モデル適格性チェック
powershell -File .loop/run-ollama.ps1 -TaskId T-XXX       # 実装
```

**モデルを入れ替えたら必ず `probe-local.ps1` を通すこと。** 実際の書き換え課題で
合否を出す。合格しないモデルを実装役に据えてはいけない。

回せるのは「1つの `function` 宣言の中で完結する変更」だけ。発注書の `## LOCAL TASKS`
に、対象の `ファイルパス :: 関数名` と英語の指示、および任意で `#### CHECK` を書く
（書式は `spec/_TEMPLATE.md`）。**これを書くのも走らせるのも親方（Sonnet 実装役）**で、
統括役ではない。仕分けの基準は `prompts/implement.md` の手順1にある。

`run-ollama.ps1` はモデルにツールもリポジトリも渡さない。関数1つを渡して書き換えた
関数1つを受け取り、**完全一致置換**で貼り付ける。差分適用とファイル全文の再生成は
小さいモデルが壊すのでさせない。貼り付け前に以下を機械で検査する（トークン0）。

| 検査 | 落とす条件 |
|---|---|
| フェンス抽出 | ` ```js ` ブロックが取り出せない |
| 無変更検出 | 出力が元コードと実質同一 |
| 関数名 | 関数名が変わっている |
| 断片の構文 | 断片単体が `node --check` を通らない |
| 既存コメント消失 | 元コードにあったコメント行が出力に無い |
| 指示に無いコメント追加 | 元にも指示文にも無いコメントが増えている（検査前に自動除去するので通常は発火しない） |
| 置換後の構文 | 置換後のファイルが `node --check` を通らない |

### 再試行の設計

トークン課金が無いので、機械検査を通るまで多めに回す（既定 12 回 / ユニットあたり上限 300 秒）。

- 1回目は temperature 0（決定的に最良を引く）。2回目以降は 0.3 / 0.5 / 0.7 を巡回しつつ **seed を振る**。
  温度だけ上げると品質が落ちるので、同じ温度で別の標本を引くほうが当たりやすい。
- **失敗理由を英語でプロンプトへ返す。** 単なる再抽選より明確に効く。

### 再試行で直るもの・直らないもの（2026-08-06 実測）

同じ課題（日本語コメント4行を含む `applyPanelAppearance`）での結果。

| 症状 | 再試行＋失敗理由の返却 |
|---|---|
| 既存コメントを削除する | **1回の再試行で解消**（消えた行を列挙して返すと直る） |
| `// Add this line` を足す | **12回中0回**。温度・seed を振っても、理由を返しても直らない |

**「〜するな」という否定制約は、何回回しても守られない。** ここは諦めて
`Remove-AddedComments` で機械的に除去している。文字列内の `//`（`'http://…'` など）を
誤って消さないよう、行内を走査してコメント開始位置を判定している。

この2つを入れた結果、**ローカルモデルの出力が Sonnet の実装と1文字も違わないもの**に
なった（T-002 の `applyPanelAppearance`、2回試行・約20秒・トークン0）。

### 重要: プロンプトは必ず英語で書く

**これが合否を分ける最大の要因だった。** 2026-08-06 の実測:

| モデル | 言語 | 結果 |
|---|---|---|
| qwen2.5-coder:3b | 日本語 | 全滅（解説文を返す / 無変更） |
| qwen2.5-coder:7b | 日本語 | 全滅（無変更 / 指示と違う変更） |
| qwen2.5-coder:7b | 英語 | 全合格（1件あたり約6.5秒） |

日本語での失敗は「指示が曖昧だから」ではない。対象コードを全文渡し、変更は1箇所、
出力の書き出しまで固定した最大限明確な条件でも、元コードをそのまま返してきた。

発注書の他のセクションは人間が読むので日本語のままでよい。`## LOCAL TASKS` だけ英語。

### 日本語コメントの多いコードでも使える

当初、日本語コメントを落とすためこのリポジトリでは使えないと判断していたが、
上記の再試行＋失敗理由の返却で解消した。適用範囲を狭める必要はない。

### CHECK ブロック（実行可能なアサーション）

適格性チェックに合格した出力にも、実際に欠陥があった。

```js
return Math.max(Number(effective) || 0, floor || -Infinity);
```

`floor || -Infinity` なので `floor: 0` を渡すとクランプが効かない。構文は正しく指示も
一見満たしているため、**機械ゲートでは絶対に捕まらない**。

ローカルLLMは再試行が無料なので、ここに実行可能なアサーションを当てられる。
発注書のユニットに `#### CHECK` を付けると、`run-ollama.ps1` が貼り付け前に実行し、
落ちたらテスト出力を英語でプロンプトに返して再試行する。

````markdown
### js/panel-util.js :: clampPanelZ

Clamp the returned value so that it is never smaller than `floor`.

#### CHECK

```js
assert.equal(clampPanelZ(-5, 0), 0);
assert.equal(clampPanelZ(3, 0), 3);
```
````

実行環境は `import assert from 'node:assert/strict'` と**その関数1つだけ**。ファイル全体は
読み込まない（`js/` の多くはブラウザ前提でトップレベルに DOM 参照を持ち、node では
import すら通らない）。したがって**自分の引数だけで完結する関数にしか付けられない**。

処理の分岐は4通り。いずれも 2026-08-07 に実機で確認済み。

| 事前確認（元コードで実行） | 挙動 |
|---|---|
| AssertionError で落ちる | 正常。判別力のある CHECK として採用し、再試行ループへ |
| 通ってしまう | 警告を出して続行（要求した変更を検証できていない） |
| それ以外のエラー | `CHECK を孤立実行できない` として**モデルを呼ばずに**ユニット失敗 |

書き換え後に CHECK が落ちた場合はファイルを書き換えず、`AssertionError` の本文を返して再試行する。
node の stderr は先頭3行が内部フレーム（`node:internal/...` / `triggerUncaughtException(`）で
埋まるため、`Format-CheckError` で Error 行以降だけを取り出してから渡している。

**CHECK があっても Sonnet の検査は外せない。** CHECK が見るのは書いた本人が思いついた
入力だけで、受入条件との照合ではない。削れるのは実装のトークンで、検査は必須。

### 抽出器を広げるべきか（2026-08-07 測定 → 結論: 広げない）

「アロー関数・クラスメソッドにも対応すれば発注量が増えるのでは」を実測で否定した。

コードベースの宣言形（`js/` 全体）:

| 宣言形 | 件数 |
|---|---|
| 列0の `function NAME()`（対応済み） | 429 |
| インデントされた `function`（ネスト） | 62 |
| 列0の `const NAME = ...`（多くはデータ定数） | 40 |
| **`class` 宣言** | **1** |
| メソッド短縮記法 | 8 |

直近25コミット・137ハンクの変更が起きた場所（波括弧の深さで分類）:

| 深さ | 件数 | 中身 |
|---|---|---|
| 0（関数の外） | 42件 (31%) | データ定義・import・トップレベル文 |
| 1 | 28件 (20%) | |
| 2 | 23件 (17%) | |
| 3以上 | 44件 (32%) | 深い入れ子 |

**トップレベルのアロー関数/関数式に入った変更は 137件中 0件。** クラスは `js/` 全体で1つだけで、
「クラスメソッドに見えた」16% の実体は `js/game-store.js` の**1311行の `dispatch`** 1つだった
（`num_ctx=8192` に入らないので、抽出できても渡せない）。

意味があるのは**領域指定の置換**（関数名ではなく一意な断片を指定して差し替える）だけ。
上表の31%と、深い入れ子の変更と、`dispatch` の `case` 1つがまとめて射程に入る。
断片単体の構文検査（`case` 節は単独で成立しない）を外し、貼り付け後の `node --check` に寄せる必要がある。

ただし**領域指定を作っても小さな1件の編集では元が取れない**（発注文を書くコストが Edit 1回と変わらない）。
効くのは「同じ変形を20箇所」のような反復作業だけ。作る前に `LOCAL-SKIP:` の集計を2〜3タスク分ためて、
`A`（単位が切り出せない）が続くかを確認すること。`B`（切り出せるが小さい）が続くなら何を作っても効かない。

## コードマップ（2026-08-08 追加）

`docs/codemap/` に、全 68 ファイルの export・シグネチャ・行番号・トップレベル関数・依存関係を
機械生成したインデックスを置く。生成は `node .loop/codemap.mjs`（トークン0）。

### なぜ入れたか

このループの支配的コストは実装役の探索で、T-001 では 102k のほぼ全部がそれだった。
原因は「統括役はソースを読むな」という鉄則の裏返しで、統括役が

- ALLOW のパスを当てずっぽうに絞る → `NEED-ALLOW:` で往復する
- `## 実装メモ` に関数名を書けない → 実装役が毎回ゼロから探す

という状態になっていた。コードマップは**ソースではない**ので、統括役が鉄則を破らずに
これらを埋められる。実装役側も、4ファイル上限を使う前にノートで当たりを付けられる。

### 設計

| | |
|---|---|
| 正 | `docs/codemap/`（git 管理）。Obsidian Vault へはスクリプトがコピーを同期する |
| 機械が持つもの | シグネチャ・行番号・関数の行数・依存グラフ・symbol の説明 |
| 人（LLM）が持つもの | `<!-- prose:summary / role / notes -->` の中だけ |

**symbol の説明はコード側のコメントが正。** export 217 件のうち 159 件（73%）は宣言直前に
JSDoc か `//` があり、生成器がそれをそのまま転記する。説明を良くしたいときはノートではなく
コードのコメントを直す。コメントが無い symbol の説明だけがノート側に保存される。

### 陳腐化の扱い

`api_sha`（export 名＋シグネチャのハッシュ）と `prose_sha` を frontmatter に持ち、
**API が変わったときだけ**散文を要更新にする。関数の中身を書き換えただけなら行番号が
更新されるだけで、散文はそのまま。本体を触るたびに要レビューが積み上がるのを避けるため。

```
node .loop/codemap.mjs --check    # 要更新のファイルだけ報告（終了コードで返す）
node .loop/codemap.mjs --accept <path>   # 散文を書き直した印を付ける
```

`gate.ps1` の `Test-Excluded` は `docs/codemap/*` を `.loop/*` と同じ扱いで除外する。
68 ノートは実装差分ではないので、数えると diff-size 上限を即座に超える。

インデックス投入で実装役のトークンがどれだけ減るかはまだ測っていない。

**分担は当面変えない。**

## 役割

| 工程 | 担当 |
|---|---|
| 発注書作成・最終承認 | Opus 5（Claude Code 本体）。ソースは読まない（`docs/codemap/` は読む）。`## LOCAL TASKS` も書かない |
| 実装（親方） | Sonnet 5 サブエージェント。コードを1回読んで仕分け、ローカルへ発注、残りを自分で実装 |
| 実装（下請け） | ローカルLLM（Ollama / qwen2.5-coder:7b）。関数単位の変更のみ。無料 |
| 検査（エラー / オーダー照合 / セキュリティ） | Sonnet 5 サブエージェント |
| 修正 | Sonnet 5 サブエージェント |

実装役・検査役・修正役は**それぞれ別のエージェント**を立てる。同じ文脈のまま検査させると
自作自演になり、検査が機能しない。

## コスト最小化の原則

1. Opus はソースを読まない。発注書と JSON の検査結果だけを見る。
2. LLM の前に `gate.ps1`（機械ゲート）を通す。ここで落ちればトークン 0 で差し戻し。
3. Sonnet に渡すのは発注書と `git diff` のみ。リポジトリ全体は渡さない。
4. 検査の出力は構造化 JSON 固定。自然言語の往復をしない。
5. ループ上限 3 周。超えたら人間へエスカレーション。

## 機械ゲートが見るもの

- ALLOW リスト外のファイルが変更されていないか
- 変更行数が上限（既定 800 行）を超えていないか。`.loop/` 配下は除外する。

## 注意: .ps1 のエンコーディング

Windows PowerShell 5.1 は BOM のない `.ps1` を ANSI として読むため、日本語コメントが
壊れてパースエラーになる。`gate.ps1` / `run-gemini.ps1` を編集したら BOM を付け直すこと:

```powershell
$p = '.loop/gate.ps1'
$t = [IO.File]::ReadAllText($p, (New-Object Text.UTF8Encoding($false)))
[IO.File]::WriteAllText($p, $t, (New-Object Text.UTF8Encoding($true)))
```
