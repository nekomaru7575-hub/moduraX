## 0-3. 再始動で入れたもの（2026-09-01）

### ① P2Pを部屋の属性にした ← 4-④の穴はこれで塞がった

**作るときに決める。** 部屋一覧の作成フォームに「P2Pで開く」を足し、`POST /api/rooms` が
`p2p` を受ける。置き場は**部屋の状態ではなく認証情報**（`server/rooms/*.auth.json` /
Redisの認証メタ、入室パスワードと同じ場所）。状態に置くとホストが権威なので、サーバーが
接続を振り分ける根拠をホストに書き換えさせることになる。

途中で切り替えられるようにはしていない。切り替えられると、サーバー権威の参加者と
ホスト権威の参加者が同時に居る瞬間ができて、そこで状態が割れる。

**接続時に振り分ける。** `wss.on('connection')` は `?net=rtc` の有無で見分ける
（ブラウザは接続先URLに `location.search` をそのまま引き継ぐ。`js/net-transport-ws.js`）。

| 部屋 | フラグ | どうなるか |
|---|---|---|
| P2P卓 | `net=rtc` あり | シグナリング接続として受ける |
| P2P卓 | なし | `4010` で断る。**中身は渡さない** |
| 従来卓 | `net=rtc` | `SIGNAL_UNAVAILABLE` を返す。中継は開かない |
| 従来卓 | なし | 今までどおり |

**`4010` は付け忘れを黙って直す。** ブラウザが `&net=rtc` を足して入り直す
（`js/net-sync.js` の `handleClose`）。逆向き（従来卓に `net=rtc` が付いていた）も
フラグを外して入り直す。notesが「実運用ではこちらの方が起きやすい」と書いた
「参加者がフラグを付け忘れる」経路が、これで存在しなくなった。

### ② ホスト役はサーバーが決める（`?host=1` は廃止）

`SIGNAL_HELLO` に `wantsHost: true` を載せ、**資格と先着でサーバーが1人だけを選ぶ**。
画面が自分で決めると2人が同時に名乗って割れるし、名乗りを検算できるのはサーバーだけ。
これで6節の「誰でも `host: true` を名乗れる」も同時に塞がった。

**`entry.hostParticipantId` が要る理由（実際に踏んだ）。** サーバーの種はP2P卓では
永遠に更新されない＝**サーバーから見ると「GMが居ない部屋」のまま**。資格の判定を
`canOperateAsGm` だけに任せると、GMがリロードした一瞬の隙に参加者がホストを名乗れて、
**GMのタブにしか無かった部屋の中身がサーバーの空の種で上書きされて消える**。
検証中に実際にこれで12件の発言が消えた。誰が務めていたかを部屋がメモリに載っている間
だけ覚えることで塞いだ。全員が抜ければ忘れる（そのときは状態も一緒に消えている）。

### ③ P2P卓ではサーバーが状態を触らない

シグナリング接続から届く `ACTION` / `REPLACE_STATE` / `SEND_STAMP` / `TYPING_*` /
`REQUEST_CHAT_SEND_SOUND` を**全部落とす**（通すのは `IDENTIFY` と `DELETE_ROOM` だけ）。
入室メッセージもP2P卓では出さない。

理由は2つ。ひとつはサーバー側に第2の権威ができて2つの部屋データが静かに食い違うこと。
もうひとつは、これが**「P2P卓ではRedisへ書かない」ことの担保**だという点——
`schedulePersistForRoom` へ辿り着く道が1本も無くなる。減らしたかった負荷そのものなので、
「来ないはず」ではなく明示的に閉じてある。

**中継そのものも従来卓では開かない**（`signalingOpen = ENABLE_P2P_SIGNALING && entry.p2p`）。
開けておくと「同じ部屋の他人へ任意のJSONを転送させる口」だけが残る。
これは攻撃テストで見つけた（`tools/p2p-attack-probe.mjs` の [4]）。

### ④ 大きいメッセージを分割する（`js/net-chunk.js`）

**疎通スパイクはINITを1発で送っていた。** DataChannelには1メッセージの上限があり、超えると
**チャネルごと落ちる**。空の部屋でしか試していなかったので露出していなかっただけで、
データURLの背景が1枚でも入れば実運用では必ず超える。上限は `pc.sctp.maxMessageSize` から
取る（決め打ちにすると、上限の小さい環境で「ある日ある部屋だけ繋がらない」形で壊れる）。

分ける単位は文字、予算はバイト。**サロゲートペアの片割れで切らない**こと——切ると送信時に
U+FFFDへ置き換わり、「絵文字の入った部屋だけ組み直せない」という形で出る。
`bufferedAmount` を見て詰まったら待つ。検証では723KBの状態が無傷で届いた。

### ⑤ 移した機能（3節の表の「動かないもの」がこれで空になった）

記入中・スタンプ・入室メッセージと入室音・チャット送信音・メッセージ流量制限・
参加者からの全データ読み込み・部屋の削除（サーバーへ中継）・入室パスワード。

移植元に無かったものが2つある。**どちらもホスト権威に特有で、抜かすと静かに壊れる**：

- **ホスト自身の分。** `js/net-sync.js` の `sendStamp` / `sendTypingStart` /
  `requestChatSendSound` はホスト時 `transport` がnullで**全部空振りしていた**
  （GMがスタンプを押しても自分にも他人にも出ない）。権威である自分に直接頼む分岐を足した。
  入室メッセージも同じで、ホストは自分の分を自分で出す（`announceSelf`）
- **記入中の一覧に自分を入れる。** サーバーは自分では書かないので移植元に無い

入室パスワードは**ホストが照合しない**。シグナリング接続がサーバーの入室門を通っているので、
DataChannelを張る時点で照合は済んでいる。`js/net-signaling.js` が `ENTRY_REQUIRED` に
`JOIN` で応えるだけで効いた。

### ⑥ 判定を純粋モジュールへ分けた（`js/net-host-rules.js`）

`js/net-host.js` は `store` と `RTCPeerConnection` に触るのでNodeから読めず、そのままでは
1行もテストできない。連打よけ・記入中の集計・入室メッセージの重複判定はどれも「境界で
1つずれる」場所なので、`js/room-authority-rules.js` と同じ流儀で分けた
（`test/net-host-rules.test.js` / `test/net-chunk.test.js` で25件）。

メッセージ流量の上限（`MESSAGE_RATE_LIMIT`）もここへ移し、**サーバーがここから読む**。
ホスト役にも同じ制限が要るので、両方に数字を書くと必ずずれる。スタンプの上限を
`js/stamp-catalog.js` に置いてあるのと同じ理由。

### ⑦ 音のURLは `/api/config` から

ホスト役は環境変数を読めない。`/api/config` は既にあったので `entrySoundUrl` /
`chatSendSoundUrl` を足し、`js/sound-config.js` が抱える（`js/asset-base.js` と同じ流儀）。
どちらも元からACTIONに載せて全員へ配っていた公開URLなので、「秘密は載せない」の線は動かない。

## 1. 出発点の分析 — サーバーの仕事は4つある

`server/index.js`（3599行）が何をしているかを分けておくこと。全部が同じ理由でサーバーに
あるわけではないので、まとめて論じると判断を誤る。

| # | 仕事 | 該当 | P2P化との関係 |
|---|---|---|---|
| A | 静的配信 | `serveStaticFile` 他 ~120行 | **P2Pと無関係**。Pages系へ置けば済む |
| B | 状態の一元化（WebSocket） | `wss.on('connection')` ~510行 | **ここがP2P化の本体** |
| C | 永続化 | Upstash Redis（`readRoomState`/`writeRoomState`/`schedulePersistForRoom`） | P2Pだと**置き場所が無くなる** |
| D | 秘密鍵を持つ中継 | R2アップロード・キャラシ取り込み ~1200行 | **P2P化できない** |

「P2Pに載せ替える」で消せるのはBだけ。A・C・Dはそれぞれ別に始末が要る。

### なぜホスト権威（案1）を選んだか

いまの同期は**サーバー権威**。クライアントは自分の画面へ先に反映してから
`ACTION{action,payload}` を投げ、サーバーが同じreducer（`js/game-store.js` をサーバーも
importしている）へ適用し、Redisへ保存し、他の全員へ配る。

- **案1（採用）: ホスト権威。** GMのタブがサーバーの役を引き受け、他はGMとだけ繋ぐスター型。
  `js/net-sync.js` は「送る／受け取る」の口だけなので**トランスポートの差し替えで済む**。
  プロトコル（INIT / ACTION / RESYNC / IDENTIFY / TYPING_USERS / ENTRY_REQUIRED …）は
  変えなくてよい。
- **案2（却下）: CRDT（Yjs / Automerge）。** `js/game-store.js` のreducerは命令的で、
  CRDTのデータモデルとは前提が違う。全面書き換えになる。プラグイン（シノビガミ・DX3・
  ステラナイツ等）が全部この上に乗っているので巻き添えも大きい。
  （凍結後に `js/store/` へ分割されて1ファイルは3716行→429行になったが、**却下の結論は
  変わらない**。分けたのはcaseが使う道具の置き場で、データモデルは命令的なまま。0-2節③）

const wantsRtc = new URLSearchParams(location.search).get('net') === 'rtc';

## 3. 何が動くか／動かないか

### 実測で通ったもの（3タブ = ホスト1＋ゲスト2）

- DataChannelが張れ、`INIT` がP2Pで届く
- チャット・コマ・パラメータがホスト⇔ゲスト双方向に流れる
- ゲスト→ホスト→**別のゲスト**への中継（スター型が成立している）
- ゲストのGM限定操作をホストが断り、`RESYNC` で画面が戻る
- 名乗った直後の連続操作が弾かれない（非同期検証のキューが効いている）
- ドラッグ相当の `MOVE_TOKEN` 40連射がすべて到達（ストア・DOMとも一致）
- ホスト不在の部屋で `?net=rtc` を開くと8秒で諦め、WebSocketへ落ちる
- **サーバーの `server/rooms/room-3.json` が空のまま** — コマも発言も参加者も1件も

## 4. 実装で踏んだ落とし穴 ← **ここが一番の資産**

下調べの時点では見えていなかったもの。再開時に同じ穴を踏まないこと。

### ① GMのタブに2つ目の `ImmutableStore` を作ってはいけない

`js/game-store.js` の `store` と `js/EventBus.js` の `EventBus` はどちらも
**モジュール・シングルトン**。`ImmutableStore#commit` はコミットのたびに
`EventBus.emit('STATE_CHANGED')` を撃つ。サーバーの `entry.store` に当たるものを
ホスト用に新設すると、**画面が他人のストアの状態で描き直される**。

→ **GM自身のストアをそのまま権威にする。** サーバーは1プロセスに複数の部屋を抱えるので
部屋ごとのストアが要るが、ブラウザは1タブ1部屋なので要らない。

### ② 本人確認が sync → async になる

サーバーの `verifyIdentity`（`server/index.js`）は `node:crypto` で同期。ブラウザ側の
同じ計算（`js/local-identity.js` の `deriveParticipantId`）は `crypto.subtle` で**非同期**。

`await` の間に届いた `ACTION` を先に処理すると、**名乗り済みのはずの人がゲスト扱いで
GM限定の操作を断られる**。しかも毎回ではなくタイミング次第なので、後から追うのが難しい
壊れ方をする。

→ ピアごとに「名乗りの検算中は後続メッセージをキューへ積む」。実装は
`js/net-host.js` の `receive()` / `handleIdentify()`。ドレインは `forEach` ではなく
**`while (!peer.identifying && peer.queue.length)`** にすること（キューの中にさらに
IDENTIFY が居た場合に順序が壊れる）。

### ③ GM限定の判定の写しが3つに増える

- `GM_ONLY_ACTIONS`（当時24項目・いま26項目）は `server/index.js` にしか無かった
- `canOperateAsGm` は server（引数を取る）と `js/room-authority.js`（グローバルを読む）で二重定義

コード中のコメント自身が「片方だけ変えるとずれる」と何度も警告していた。ホスト役が
3つ目の写しを持つと事故が確定する。

→ `js/room-authority-rules.js`（純粋関数だけ・環境依存物に触れない）へ寄せた。
**これはP2Pと無関係にも効く改善なので、実験を巻き戻しても残すこと。**

なお、サーバーが読むのは `js/room-authority-rules.js` であって `js/room-authority.js`
ではない。後者は `store` と `net-sync.js` 経由で `location` に触れるためNodeから読めない。

**凍結中の答え合わせ: これは効いた。** GM限定の判定が2件増えたが、直したのは共有モジュール
1ファイルだけで3か所が揃い、写しがズレた事故は0件だった（0-2節⑤）。

### ④ フォールバックを片側にしか作らなかった ← **2026-09-01に解決（0-3節①）**

**塞ぎ方は下の「直し方」の案1（P2Pを部屋の属性にする）。** 以下は当時の記録として残す——
なぜ割れるのかの筋道は、次にフォールバックを足すときにそのまま効く。

参加者側は、WebRTCが張れなければ8秒でWebSocketへ落ちる。**ホストは落ちない。**

結果、落ちた参加者は「サーバーが権威の部屋」へ、ホストは「自分が権威の部屋」に残り、
**黙って2つのセッションに割れる**。ホストのシグナリング用WebSocketはサーバーから流れて
くる `ACTION` を読み捨てている（`js/net-signaling.js` は `SIGNAL_*` と最初の `INIT`
しか見ない）ので、参加者の操作は永久にホストへ届かない。

エラーも警告も出ない。気づけるのは「同期しない」という症状だけ。**併存を選ぶなら、
ここを塞がずに先へ進んではいけない。**

同じ症状は「参加者が `?net=rtc` を付け忘れた」でも起きる。通常の部屋URLを渡すと確実に
こうなるので、実運用では(A)の方が起きやすい。

→ **こちらは付け忘れそのものを無くした。** サーバーが `4010` で断り、ブラウザがフラグを
足して入り直す（0-3節①）。古いURLやブックマークで来ても、利用者は何も気づかない。

#### 切り分け方

ホスト側のコンソールに `[net-host] 参加者が繋がりました（現在N人）` が出ているか。

- 出ていない → 参加者はP2Pに繋がっていない。参加者側に
  `[net-transport] WebRTCで繋がらなかったので…` があればRTC失敗、無ければフラグ付け忘れ
- 出ている → P2Pは繋がっているので別の原因

#### 直し方（3案。性格が違う）

1. **P2Pかどうかを部屋の属性にする（推奨）** — サーバーは誰がホストを名乗ったか知っている
   ので、フラグ無し／RTC失敗の接続には部屋の中身を渡さず「この部屋はP2Pで開かれています」と
   断る。**割れる代わりに、繋がらない人がはっきり分かる。** 目的（常時サーバーを無くす）に
   一番忠実。
2. **ホストがサーバーへ書き戻す** — ホストが受けた操作をシグナリングWS経由で `ACTION` として
   流す。WS参加者もそのまま遊べ、**Redis永続化も戻る**。ただしサーバーの負荷は減らないので
   P2P化の旨みはほぼ消える。「P2Pは高速化の手段、サーバーが背骨」という別の設計。
3. **ホストにもフォールバックを付ける** — 一定時間ピアが繋がらなければホスト役を降りて
   通常のWSクライアントに戻る。実装は軽いが、途中で権威が入れ替わるぶん状態の扱いが厄介。

## 5. 正直に詰まるところ（下調べ時点の見立てと、実験後の答え合わせ）

### 5-1. シグナリングサーバーは結局要る → **その通り。ただし思ったより軽い**

WebRTCは相手を見つける仲介が必ず要る。「サーバーが無くなる」のではなく、**常時起きている
大きなサーバーが、繋ぐ瞬間だけの小さなサーバーになる**。

実装してみると中継は `SIGNAL_HELLO` と `SIGNAL` の2つだけ、**中身を一切解釈しない郵便受け**
で済んだ。第三者の公開シグナリング（Trysteroのnostr/MQTT、PeerJSの公開サーバー）に部屋の
生死を預けるより、どのみち残るこのサーバーに置く方が短い。

### 5-2. NAT越え（TURN） → **未検証。最大のリスクのまま**

Symmetric NAT下ではSTUNだけでは繋がらず、TURN中継が要る。実測で1〜2割は踏むと言われる。
**今回はlocalhostでしか試していないので、この数字は確かめていない。**
「たまに繋がらない人が出るセッションツール」はTRPGの用途だとかなり痛い。

### 5-3. GMが落ちたら部屋が消える → **実装のとおりそうなった**

いまはRedisに `room:room-N` があるので全員が抜けても部屋は残る。ホスト権威P2Pだと状態は
GMのタブの中にしか無い。**GMがタブを閉じた／回線が切れた＝セッションが飛ぶ。**
しかもホストがリロードすると、サーバーの凍った状態から種を取り直すので巻き戻る。

緩和: IndexedDBへ保存してリロードで復帰、定期の自動エクスポート、または上の④-2案。
ただし「GMが落ちている間、他の人は何もできない」のは緩和できない。

### 5-4. R2アップロードはP2P化できない → **確定**

`/api/image` `/api/audio` はR2の署名にアクセスキーが要る（`server/r2.js`）。ブラウザへ鍵を
置けば**そのまま流出＝課金事故**で、これは守ると決めた範囲のど真ん中。選択肢:

- (a) 署名発行だけの極小関数を残す（＝完全なサーバーレス化は諦める）
- (b) 画像をDataChannelで直接配る（音源20MBはつらい。`js/image-upload.js` は6モジュールから使われている）
- (c) アップロード機能を落として外部URLのみにする

**未決のまま凍結。** 併存を採る限りWSサーバーは残るので、先送りしても実験の妨げにならない。

### 5-5. キャラシ取り込みはCORSで直叩きできない → **確定**

`/api/character-sheet` は「外部のキャラクターシート置き場がCORSを許していないので代わりに
取りに行く」中継。**ブラウザからは代替不能。** 5-4と同じ判断が要る。

### 5-6. BCDiceは直叩きできる → **その通り。実装済み**

`js/BCdice.js` が既に `https://bcdice.onlinesession.app` を直接叩けている＝CORSは通る。
`/api/bcdice/*` はキャッシュと堅牢化のためのproxyであって**CORS回避ではない**。

一次取得先をBCDice本体へ入れ替えた（システム一覧336件を直接取得、`/api/bcdice/*` への
リクエストゼロを確認）。中継は控えとして残してある。CSPの `connect-src` には元から
BCDiceのオリジンが入っていたので追加設定は不要だった。

### 5-7. 部屋一覧が無くなる → **手つかず**

`/api/rooms` の一覧・作成・パスワード設定（`js/room-index.js`）はサーバー前提。P2Pだと
「GMが出したURLを配る」形になる。スパイクではホストを `&host=1` の明示指定にして回避した。

## 6. デプロイして分かったこと

Renderへ `w2p-migration` を出して確認済み。

- **既定の挙動はmainと同一。** 画像アップロード→R2も従来どおり動いた。
  アップロード経路（`server/r2.js` / `js/image-upload.js` / `handleMediaUpload` / `putObject`）は
  **1バイトも変わっていない**
- **利用者から見える違いは実質1つだけ** — BCDiceの取得先（5-6）。副作用としてUpstashの読み込みが減る
- **mainへ戻すのも安全。** 永続化の形式・Redisキー・`CURRENT_AUTH_VERSION`（=3）を触っていない。
  main のworktreeを作り、w2pが書いた部屋データ3件を main のコードで
  `hydrate` → `dispatch` → `adoptImportedState` まで通して確認済み
- localStorageの新規キーなし、`sw.js`/`manifest.webmanifest` は無変更。JSは `no-cache` かつ
  Service Workerがキャッシュしないので、リロードで戻る
- 切り替えの瞬間に古いページを開いたままの人がいても、`SIGNAL_*` は main のサーバーで
  `if (message.type !== 'ACTION') return;` に落ちて黙殺される。落ちない

### RTCモードでのRedis

- **書き込みはゼロ。** Redisへ書くのは `ACTION` / `IDENTIFY` / `REPLACE_STATE` の3つだけで、
  RTCクライアントがWSへ送るのは `SIGNAL_HELLO` と `SIGNAL` のみ
- **読み込みは1回だけ** — ホストが繋いだ瞬間の `getOrLoadRoom`（これがホストの種になる）
- 結果、**Redis上の部屋データはホストが入った瞬間の姿で凍る**（＝5-3そのもの）
- 部屋の作成と入室パスワード設定はHTTP経路なので、RTCモードでもRedisに書く

### シグナリング中継は既定で閉じてある

`SIGNAL` 中継だけは、`?net=rtc` と無関係に**全接続から届く口**になる。他のP2Pコードは
フラグが無ければ1行も動かないが、ここだけは違う。凍結中は誰も使わないので、
**`ENABLE_P2P_SIGNALING=1` を明示したときだけ通す**ようにしてある（既定は閉じる）。

脅威モデル
（守る: サーバー本体・課金・保存型XSS／守らない: なりすまし）に照らすと:

- サーバー・課金 — レート制限と大きいフレームのメモリ検査の**後ろ**にあり、Redis書き込みも
  R2アクセスも起こさない。守れている
- 他人のブラウザ — RTCモードでないクライアントは `{type:'SIGNAL'}` を全分岐素通りで無視。
  DOMに入らないのでXSS経路にならない
- **ただし誰でも `host: true` を名乗れる。** 同じ部屋の悪意ある参加者が、後からRTCで入る人に
  とっての「ホスト」になりすまし、同期経路を握れる。なりすましは意図的に守らない範囲だが、
  **新しく増えた経路**。中継を開けるとき（＝再開するとき）は、先に `SIGNAL_HELLO` を
  名乗り済みのGMだけに限ること（`canParticipantOperateAsGm` を通す）
